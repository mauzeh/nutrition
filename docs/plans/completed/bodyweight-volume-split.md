# Bodyweight Volume Split — Logger Plan (reference architecture)

> This is the PLAN (context + architecture). Execute from `bodyweight-volume-split-prompt.md`.

## Problem Statement

The `bodyweight` PR family (`config/pr_families.php`) has one `volume` descriptor that serves two
incompatible quantities:

- **Weighted** bodyweight session (Dips +25 lbs × 6 × 4) → volume = Σ(weight×reps) = 600 (a mass-weighted
  volume).
- **Pure-bodyweight** session (5,7,8,8 all weight 0) → volume = Σ(reps) = 28. `Reductions::sumProduct` has
  an `$allZeroWeight` branch that substitutes weight=1 when every set is zero-weight, collapsing the product
  to a rep sum.

Both persist as `pr_type = 'volume'` and compare via `Comparators::scalarBest` (max). So a later
pure-bodyweight 28-rep session cannot beat an earlier weighted 600. And the display
(`PRRecordsComponentAssembler`) derives an `isPureBodyweight` flag AT DISPLAY TIME from the current log's
`exercise_type` + the row's `weight` (always null for volume), so a stored weighted 600 is shown with the
bodyweight label + reps format → "600 reps". 600 is pound-reps, not reps.

## The Fix

Split the `bodyweight` family's single volume descriptor into two mutually-exclusive `pr_type` tracks. A log
is either weighted (some set weight > 0) or pure-bodyweight (all zero) — exactly one fires per log.

| | Weighted (unchanged) | Bodyweight (new) |
|---|---|---|
| pr_type | `volume` | `bodyweight_volume` |
| factors | `['load','reps']` | `['reps']` |
| fires when | some set weight > 0 | all sets weight = 0 |
| value | Σ(weight×reps) | Σ(reps) |
| tolerance | `percent` | `none` |
| label / format | `Volume` / volume | `Total Reps` / reps |
| kg de-normalized? | yes (mass) | NO (rep count) |

Scope: `bodyweight` family ONLY. Every other family untouched. `pr_type` is VARCHAR(32) (migration
`2026_08_31_145200`), and `bodyweight_volume` is 17 chars → NO schema migration needed.

## Architecture (mirrors the existing config-driven engine)

1. **Config** (`config/pr_families.php`): `bodyweight` family gains a `mode` on the weighted `volume`
   descriptor and a new `bodyweight_volume` descriptor (per frozen spec). No other family changes.
2. **Reduction** (`app/Services/PR/Reductions.php`, `sumProduct`): honor `$descriptor['mode']`. Weighted
   descriptor returns null/skips all-zero-weight logs; bodyweight descriptor (factors `['reps']`) returns
   null when any set has weight. Remove the `$allZeroWeight`→substitute-1 branch (the mode split replaces it).
3. **History + detection** (`app/Services/PRDetectionService.php`): `buildHistoryFromPreviousLogs` and
   `detectPRsWithDetails` already dispatch off descriptor `type`/`compare`, so the two scalar tracks fold
   into independent `$history['volume']` and `$history['bodyweight_volume']` entries with no structural
   change. EXCLUDE `bodyweight_volume` from the kg de-normalization whitelist (currently `['one_rm',
   'rep_specific', 'volume', 'load']`) — it is a rep count, mirroring how `hypertrophy` is already excluded.
4. **Persistence + chains** (`app/Services/PRRecalculationService.php`): `PersonalRecord::create` writes
   `pr_type` verbatim (no change), and `chainKey` groups scalars by `pr_type`, so `bodyweight_volume` forms
   its OWN supersession chain automatically — the two tracks never supersede each other.
5. **Display** (`app/Services/LiftLogTableRowBuilder/PRRecordsComponentAssembler.php`): replace the
   display-time `isPureBodyweight` heuristic (which reads the current log, not the stored row) with a
   decision driven by the stored `pr_type`: `volume` → "Volume"/weight format; `bodyweight_volume` →
   "Total Reps"/reps format. A stored weighted 600 always renders as "Volume 600", never "600 reps".

## Consumer Impact Trace (data-shape change: pr_type semantics)

- **Readers of pr_type `volume`:** `PrEngine::detectPRs`, `PRDetectionService` (history fold + kg whitelist),
  `PRRecalculationService` (create + chainKey), `PRRecordsComponentAssembler` (label/format), chart
  generators, and any PR-table/feed consumer. After the split, `volume` is weighted-only; a new
  `bodyweight_volume` token carries the pure-bodyweight rep count.
- **kg whitelist** (`PRDetectionService::detectPRsWithDetails`): `bodyweight_volume` must NOT be in the
  mass-conversion `in_array(...)` list.
- **Display heuristic:** the `isPureBodyweight` derivation in `PRRecordsComponentAssembler` is replaced by a
  `pr_type` check. Grep for `isPureBodyweight` and `bodyweightLabel` to find every site.
- **Tests asserting `pr_type = 'volume'` for bodyweight-reps logs:** update to expect `bodyweight_volume`
  for pure-bodyweight.
- **Existing records:** regenerated by re-running `prs:calculate-historical` after deploy (delete-then-rebuild
  splits old single-track volume rows into the two tracks). No data-migration script; pr_type is varchar.

## Success Criteria

- Weighted bodyweight session → `pr_type = 'volume'` (Σ weight×reps), label "Volume".
- Pure-bodyweight session → `pr_type = 'bodyweight_volume'` (Σ reps), label "Total Reps".
- Dips anchor: weighted 600 then pure-BW 28 (prior BW best 24) → a `bodyweight_volume` PR fires (value 28,
  previous 24); the weighted `volume` best (600) is untouched and renders as "Volume", never "600 reps".
- `bodyweight_volume` never kg-converted.
- Every other family byte-identical. Full `php artisan test --parallel` green.

## Risks

- **Shared model / web UI.** `PRRecordsComponentAssembler` feeds the lift-log table and mobile summary —
  run the full suite; existing bodyweight display tests must still pass with the new label routing.
- **Chain relinking.** Confirm `chainKey`'s default (scalar → key by `pr_type`) already isolates the new
  token (it does — no change needed, but a test should assert the two tracks don't cross-link).
- **Equivalence contract.** Must mirror the Athlete slice exactly (same tokens/factors/labels/tolerance) or
  the root equivalence suite fails when it runs later.
